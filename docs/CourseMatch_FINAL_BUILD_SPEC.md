## 3. Final decisions

**Chat routing.** Claude is the primary chat parser whenever a valid key is present. The key-free rule parser is the fallback whenever the key is missing, still the placeholder, or any Claude call fails. Adding the key to `.env` switches routing on the next chat message with no restart and no code change.

**API key placeholder.** `.env.example` contains `ANTHROPIC_API_KEY=sk-ant-REPLACE_ME`. A key is valid only if it is non-empty, starts with `sk-ant-`, and does not contain `REPLACE_ME`.

**Model.** Default model id `claude-sonnet-5-5`, overridable with `COURSEMATCH_LLM_MODEL` in the environment or `.env`. Temperature 0. Timeout 10 seconds. One retry.

**The language model never ranks, never writes an explanation, never states a prerequisite.** Every model output passes the existing `validate()` before anything is written. Explanations shown in chat come from `explain.py`.

**Profile page.** Added. Shows what the student stated and what the system inferred. Inferred interests can be removed and restored. Removal is sticky: later saves and dismissals still record evidence but do not reactivate a removed inference.

**Taxonomy.** Extended with 10 electrical engineering topics. This deliberately changes the earlier "fixed taxonomy" rule, because 26 recommendable ECEN courses currently have no topic.

**Topic labels.** The key-free method selected by the comparison remains the base. When a valid key is present, an LLM pass adds labels with `source='llm'`, which `topics.py` already prefers.

**Study.** Within-subject. CourseMatch against BM25 keyword search. Two task sets, counterbalanced into four orders. Participants shortlist three courses for a sample student. Unmoderated flow at `/study`, the same flow used for the moderated sessions. Primary measure: number of the three chosen courses that are feasible for the sample student.

**Study data stays out of git.** The study runs against a copy of the database, `data/study/study_run.db`, which is ignored.

## 6. W3 — LLM access layer and chat routing

### 6.1 New file `backend/app/llm.py`

The single place that reads the key and calls Anthropic. Both the chat and the topic pass use it.

```python
PLACEHOLDER = "sk-ant-REPLACE_ME"
DEFAULT_MODEL = "claude-sonnet-5-5"
TIMEOUT_S = 10.0
MAX_RETRIES = 1

class LLMUnavailable(Exception):
    def __init__(self, reason: str, detail: str = ""):
        # reason is one of:
        # "no_api_key", "auth_error", "model_not_found", "rate_limited", "timeout", "api_error"
        ...

def get_api_key() -> str: ...
def key_is_valid(key: str) -> bool: ...
def get_model() -> str: ...
def get_chat_mode() -> str: ...
def complete(system: str, user: str, max_tokens: int = 300) -> str: ...
```

Rules:

- **`get_api_key()`** reads the value on every call, never cached. If `ANTHROPIC_API_KEY` is set in the process environment and is valid, return it. Otherwise read `ROOT/.env` fresh with `dotenv.dotenv_values` and return its `ANTHROPIC_API_KEY`, or `""`.
- **`key_is_valid(key)`** returns true only when the key is non-empty, starts with `sk-ant-`, and does not contain `REPLACE_ME`.
- **`get_model()`** returns `COURSEMATCH_LLM_MODEL` from the process environment, else from `.env` read fresh, else `DEFAULT_MODEL`.
- **`get_chat_mode()`** returns `COURSEMATCH_CHAT` from the process environment, else from `.env` read fresh, else `"auto"`, lowercased. Any value other than `auto`, `rules`, `claude` is treated as `auto`.
- **`complete()`** raises `LLMUnavailable("no_api_key")` when the key is invalid. Otherwise it calls `anthropic.Anthropic(api_key=key, timeout=TIMEOUT_S, max_retries=MAX_RETRIES).messages.create(model=get_model(), max_tokens=max_tokens, temperature=0, system=system, messages=[{"role": "user", "content": user}])` and returns the concatenated text blocks. Cache one client per key value.
- **Exception mapping inside `complete()`:** `anthropic.AuthenticationError` and `anthropic.PermissionDeniedError` → `auth_error`; `anthropic.NotFoundError` → `model_not_found`; `anthropic.RateLimitError` → `rate_limited`; `anthropic.APITimeoutError` → `timeout`; any other exception → `api_error`. Write one line to stderr per failure: `[llm] <reason>: <exception class>`. Never print the key.

### 10.3 Order assignment

When a new participant code starts, assign the `order_index` with the fewest participants already assigned. Break ties by lowest index. Deterministic and balanced; never random.

### 10.4 Endpoints

All under `/api/study/`. Codes must match `code_pattern`, otherwise 422 `{"error":"invalid_code"}`.

**`POST /api/study/start`** `{"participant_code": "P001"}`
Creates the participant if new, assigning an order. Response:

```json
{
  "participant_code": "P001",
  "order_index": 2,
  "consented": false,
  "steps": ["consent", "practice", "task:B", "questionnaire:B", "break",
            "task:A", "questionnaire:A", "final", "done"],
  "next_step": "consent"
}
```

`steps` is built from the assigned order. `next_step` is the first incomplete step, so a participant who closes the browser resumes where they stopped.

**`POST /api/study/consent`** `{"participant_code"}` sets `consent_at`. Returns the start response with the updated `next_step`.

**`POST /api/study/task/start`** `{"participant_code", "task_id"}`
Refuses with 409 `{"error":"out_of_order"}` if this is not the `next_step`, and with 403 `{"error":"no_consent"}` before consent. Creates a new student with the task's condition, copies the task's sample profile onto it using the existing sample loading logic, and inserts or reuses the `study_sessions` row.

```json
{
  "student_id": "s_ab12cd34",
  "condition": "system",
  "task_id": "A",
  "prompt": "...",
  "required": 3,
  "profile": {
    "program": "MSCS",
    "completed_courses": [{"code": "CSCE 625", "title": "..."}],
    "interests": ["machine learning", "computer vision", "deep learning"]
  }
}
```

If the session already exists and is not submitted, return the same `student_id`, so the student's searches and saves survive a reload.

**`POST /api/study/task/submit`** `{"participant_code", "task_id", "course_codes": [...]}`
Requires exactly `required` distinct codes. Every code must exist and have `is_recommendable=1`, otherwise 422 with the offending codes. Stores `answer_codes`, `submitted_at`, and `duration_s` measured from `started_at`. Returns the updated `next_step`.

**`POST /api/study/questionnaire`** `{"participant_code", "task_id", "responses": {"usefulness": 5, ...}}`
Requires all five item ids, integer values 1 to 7. Stores one `study_responses` row per item.

**`POST /api/study/final`** `{"participant_code", "answers": {"why_chosen": "...", "distrust": "...", "own_semester": "..."}}`
Stores three rows with `task_id=null`, sets `completed_at`.

**`GET /api/study/progress/{participant_code}`** returns the start response.

The `break` step is completed by the client calling `POST /api/study/break_done {"participant_code"}`.

Responses never reveal scores, feasibility, or correct answers.

### 10.5 Changes to existing endpoints

- **`GET /api/courses/autocomplete`** gains `recommendable_only: bool = False`. When true, only courses with `is_recommendable=1` are returned.
- **`GET /api/baseline/search`** gains an optional `student_id`. When present, the server logs a `search` event with condition `baseline` and payload `{"codes": [returned codes in order], "returned_count": n}`. The frontend baseline page stops logging `search` itself and passes its student id instead.
- **`/api/recommend`** adds `"codes": [returned codes in order]` to the payload of the `search` event it already logs.

### 10.6 Scripts

## 12. W9 — Study scoring and analysis

### 12.1 `scripts/study/answer_keys.py`

For each scored task, writes `data/study/answer_keys.json`: every recommendable course with its readiness state for that task's sample profile, and whether it is feasible. For the facilitator only; never served by the API.

### 12.2 Feasibility, exact definition

A chosen course is feasible for a sample profile when all of these hold:

- It is not in the profile's completed courses.
- `readiness.assess(code, completed)` returns `ready` or `not_sure`. `not_sure` counts as feasible, because the catalog names no course prerequisite, so nothing blocks registration for a graduate student.

The feasibility score of a task is the number of chosen courses that are feasible, 0 to 3. The profile used is the sample profile from `samples.json`, not the session student's profile, so anything a participant changes during the task cannot affect scoring.

Secondary score: `fit` is the number of chosen courses that share at least one `covers` topic with the sample profile's stated interests.

### 12.3 `scripts/study/analyze.py`

Reads the database named by `COURSEMATCH_DB`. Writes `docs/STUDY_RESULTS.md`.

**Exclusions**, applied before any analysis and reported with counts and reasons:

- Did not complete both scored tasks.
- Total time across both scored tasks under 120 seconds.
- Identical `answer_codes` sets in tasks A and B.

**Per participant and condition:** feasibility score, fit score, task duration, the five questionnaire items, and the rank of each chosen course in the last `search` event of that session that contained it. Report `not shown` when the course never appeared in a logged result list.

**Primary test.** Wilcoxon signed-rank on feasibility score, system against baseline, using `scipy.stats.wilcoxon(x, y, zero_method="wilcox")`. Report the number of non-tied pairs, the W statistic, the p value, and the matched-pairs rank-biserial effect size, computed as the sum of positive ranks minus the sum of negative ranks, divided by the total rank sum, over non-tied pairs.

**Exploratory tests.** The same test and effect size for fit, duration, and each questionnaire item, in a separate table headed `Exploratory`.

**Order and task checks.** Median feasibility and duration by task set within the baseline condition only, and by position, first or second.

**System-only feature use**, from `interactions` for study sessions in the `system` condition: share of sessions that opened "Why this?" at least once, mean expansions per session, share of sessions that used chat, chat messages by `backend_used`, clarifications shown, answered and dismissed, profile views, inferences removed.

**Open answers.** All three final answers per included participant, verbatim, grouped by question.

If fewer than 8 participants remain after exclusions, the report states this at the top and still produces all tables.

A small synthetic dataset in `backend/tests/test_study_analysis.py` checks the feasibility definition, the exclusion rules, and the effect size calculation against a hand-computed example.
